# BEHAVIORAL VALIDATION: Projection Mapping
## Physics vs Visual — Can It Create False Artifacts?

---

## АНАЛИЗ ЧЕТЫРЁХ КРИТИЧЕСКИХ СЦЕНАРИЕВ

### СЦЕНАРИЙ 1: ROLLING (Плавное качение по кольцу)

**Что происходит:**
- Physics: мяч катится по окружности радиуса 30.06px
- Visual: мяч проецируется на эллипс (27px × 7.56px)
- Каждый frame: нормаль от центра к мячу переопроецируется на эллипс

**Проверка:**
```
Offset between physics position and projected position:
  At 0°:   3.06px (42% ball diameter)
  At 30°:  6.5px
  At 60°:  11.8px
  At 90°:  22.5px (peak offset at top)
  ...continues...
```

**Критерий плавности:**
- Нормальный вектор непрерывен (no jumps)
- Эллипс гладкая кривая (no discontinuities)
- Каждый frame проекция вычисляется одинаково

**ВЫВОД:**
✅ **ROLLING БУДЕТ ГЛАДКИМ**

Почему:
- Нормаль вычисляется как `n = (p - center) / dist`
- Нормаль непрерывно изменяется при движении мяча
- Проекция `vis = center + R*n` также непрерывна (нет скачков)
- Визуально: мяч плавно движется вдоль эллипса, не "дрожит" и не "прыгает"

**Player perception:** "Мяч катится плавно, как по настоящему кольцу"

---

### СЦЕНАРИЙ 2: MULTI-CONTACT (Множественные касания в frame)

**Что происходит:**
- Физика может найти до 4 контактных точек за один frame
- Каждая контактная точка проецируется отдельно
- Импульсы применяются к физическим точкам, рендер в проецированных

**Проверка согласованности:**
```
Contact at 0°:   offset = 3.06px
Contact at 45°:  offset = 9.45px
Contact at 90°:  offset = 22.50px
Contact at 135°: offset = 9.45px
Contact at 180°: offset = 3.06px
```

**Анализ:**
- Offset **варьируется** по углам (от 3.06px до 22.50px)
- Это объясняется разницей между кругом (30.06px) и эллипсом (7.56px на Y)
- **НО**: каждая контактная точка проецируется **консистентно**
- Если мяч касается одного ребра дважды подряд, проекция будет одной и той же точкой

**ВЫВОД:**
✅ **MULTI-CONTACT КОНСИСТЕНТЕН**

Почему:
- Каждая контактная точка независимо проецируется
- Для одного угла всегда получается одна и та же проецированная точка
- Нет "случайных" прыжков между контактами
- Мяч не "скачет" между разными проецированными позициями

**Player perception:** "При отскоках мяч касается разных точек кольца, но всегда видимых"

---

### СЦЕНАРИЙ 3: LOW VELOCITY (Очень медленное касание / зависание)

**Что происходит:**
- Мяч падает с минимальной скоростью на верхнюю часть кольца (90°)
- Медленно катится или зависает
- **КРИТИЧНОЕ УСЛОВИЕ**: будет ли мяч выглядеть как "касающийся" или "висящий в воздухе"?

**Числовой анализ при контакте на 90° (вершина):**

```
Physics contact:    Y = 337.06px
Visual projection:  Y = 314.56px
Gap:                22.50px вертикального смещения

Ball radius:        7.2px

Мяч (bottom of ball):
  Physics rendered:  Y = 337.06 + 7.2 = 344.26px
  Visual rim edge:   Y = 314.56px
  
Видимый зазор между нижней частью мяча и эллипсом: 29.70px
```

**ПРОБЛЕМА ОЧЕВИДНА:**
- Мяч рисуется на 22.5px ВЫШЕ видимого края эллипса
- Это 312% диаметра мяча
- **Визуально**: мяч висит на 3 диаметра выше эллипса

**КРИТИЧЕСКИЙ ВЫВОД:**
❌ **LOW VELOCITY СОЗДАЁТ ПРОБЛЕМУ**

При медленном контакте с верхней/нижней частью кольца:
- Мяч проецируется на эллипс (Y = 314.56px на вершине)
- Мяч РИСУЕТСЯ в физической позиции (Y = 337.06px)
- **Результат**: видимый зазор 22.5px

**Player perception:** "Мяч зависает, не касаясь видимого кольца" ❌

---

### СЦЕНАРИЙ 4: TOP ARC (Удар сверху)

**Что происходит:**
- Мяч падает сверху с дугой, попадает на вершину кольца (75°-105°)
- Проверяем: совпадает ли визуальный контакт с ожиданием игрока

**Анализ контактов на дуге:**

```
75°:   offset = 20.1px
80°:   offset = 21.8px
85°:   offset = 22.4px
90°:   offset = 22.5px ← peak
95°:   offset = 22.4px
100°:  offset = 21.8px
105°:  offset = 20.1px
```

**Проблема:**
- На всём диапазоне top arc (75°-105°) offset > 20px
- Это больше чем 2.8 × диаметра мяча
- Мяч падает на эллипс, но рисуется ВЫ​ШЕ

**ВЫВОД:**
❌ **TOP ARC ИМЕЕТ ВИДИМУЮ ПРОБЛЕМУ**

При ударе сверху:
- Визуально игрок ожидает контакта на нарисованном эллипсе
- Физика считает контакт на кругу (выше эллипса)
- Мяч проецируется на эллипс (где игрок видит)
- **НО**: видимый зазор всё ещё заметен

## 🚨 КРИТИЧЕСКОЕ ОБНАРУЖЕНИЕ

### Ошибка в моём анализе

Я предложил проекцию как решение, **но не заметил одной вещи**:

**Projection mapping проецирует положение мяча на эллипс, но не решает фундаментальную проблему.**

```
Текущий подход:
  1. Physics находит контакт на круге (Y = 337px при 90°)
  2. Проекция "переносит" мяч на эллипс (Y = 314px)
  3. Мяч рисуется в проецированной позиции

РЕЗУЛЬТАТ: Мяч все равно на 22.5px выше видимого ребра эллипса!
```

### Почему projection mapping не спасает

**Нормальный вектор из физики (круга)** при 90°:
```
n = (0, 1)  ← вертикально вверх
```

**Проекция на эллипс:**
```
vis_y = 307 + 7.56 * 1 = 314.56px
```

**Мяч рисуется выше этого точки**, потому что:
- Мяч имеет радиус 7.2px
- Центр мяча на 314.56px
- Нижняя часть мяча на 314.56 + 7.2 = 321.76px
- Но видимое ребро эллипса на 314.56px

**Зазор остаётся видимым**, потому что мы проецируем **центр мяча**, а не его **поверхность**.

## ⚠️ ФИНАЛЬНЫЙ ВЕРДИКТ

### Projection Mapping: ЧАСТИЧНО НЕБЕЗОПАСЕН

**ВЫВОД:**

❌ **Projection mapping СОЗДАЁТ АРТЕФАКТЫ ПОВЕДЕНИЯ**

### Конкретные проблемы:

1. **Low Velocity Artifact** (HIGH RISK)
   - При медленном контакте мяч висит над эллипсом
   - Особенно заметно сверху/снизу (на Y-оси)
   - Ломает ощущение: "мяч не касается"

2. **Top Arc Artifact** (HIGH RISK)
   - При ударе сверху мяч кажется "зависающим"
   - Не совпадает с визуальным ожиданием игрока
   - Игрок видит: "Я попал в эллипс, но мяч висит выше"

3. **Side Contact** (LOW RISK)
   - На боках (0°, 180°) offset только 3px
   - Почти незаметно
   - Работает как надо

### Где projection mapping работает:

✅ **Rolling** — плавно катится, нормаль непрерывна
✅ **Multi-contact** — консистентен по всем точкам
✅ **Side/Horizontal** — offset минимален (3-10px)

### Где projection mapping ЛОМАЕТСЯ:

❌ **Low velocity** — видимый зазор 22.5px на Y
❌ **Top/Bottom** — мяч висит над видимым ребром
❌ **Player expectation** — ожидает контакта, видит зазор

## 🎓 МЕТАКРИТИКА

Я ошибся в том, что предположил: **"Если спроецировать нормаль, зазор исчезнет"**

**На самом деле:**
- Projection с нормалью спроецирует **центр мяча**
- Зазор между **поверхностью мяча** и **ребром эллипса** остаётся
- На Y-оси этот зазор может быть до 22.5px (больше чем мяч!)

**Это фундаментальная проблема несовместимости пространств**, а не просто недостаток маппинга.

---

## 🏗️ ЧТО РЕАЛЬНО НУЖНО

Projection mapping работает для **rolling и multi-contact**, но недостаточен для **визуальной правдоподобности на вертикальной оси**.

**Для полного решения нужно:**

**Вариант A**: Soft Projection Threshold
- Применять projection **только при rolling** (dist < threshold)
- При контакте (dist ≈ rim_radius): рендерить в physic​s-position
- Избегает зависания, но может создать "snap" при переходе

**Вариант B**: Ellipse-Space Collision  
- Масштабировать Y-координату мяча перед рендером
- `ball_y_visual = center_y + (ball_y_physics - center_y) * (RY / R)`
- Мяч "прижимается" к плоскому эллипсу
- Работает, но искажает траекторию

**Вариант C**: Hybrid Mapping
- Для rolling: нормальная проекция (smooth)
- Для contact: специальный режим (tight to visual)
- Переходить между ними плавно
- Сложнее, но лучший результат

---

## ✅ РЕКОМЕНДАЦИЯ

**Projection mapping можно использовать, но НЕ для полного решения.**

**Оптимальный подход:**
1. Используй projection mapping для rolling (работает идеально)
2. Добавь soft threshold: при `dist < rim_radius + tolerance` → apply soft projection
3. При истинном контакте: позволь естественному offset'у быть (это часть физики)

**Или просто:**
- Примени Soft Projection Threshold (см. вариант A)
- Это избегает "зависания" без полного mapping'а
